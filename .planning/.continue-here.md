<decisions_made>

- Task é first-class (tabela própria), não jsonb — para individualizar pontos por operacional
- Dois Kanbans separados: funcionalidades (já existe, não muda) + tasks (novo)
- Só 3 colunas (planejado/em_andamento/concluida) — sem Em Review/Bloqueado como coluna
- Bloqueado = flag booleana na task, não coluna separada
- Operacional é entidade por projeto (não global) — sem tabela pessoas global no MVP
- SPI por sprint via pontos (EVM): Σ pontos_realizados / Σ pontos_previstos
- Sem importador de planilha CCE — gerentes cadastram tasks manualmente
- Sem campo `tipo` (dev/design/etc) nas tasks
- Backlog → planning: Kanban alimenta o rascunho do composer automaticamente
- Review → Kanban: match fuzzy propõe sugestões, gerente aceita/rejeita (nunca aplica automaticamente)
- `_registrar_task_transicao` calculado em Python no handler PATCH (mesmo padrão Phase 7 de transicoes_status)
</decisions_made>
