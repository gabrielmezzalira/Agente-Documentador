<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent cliente → POST /ingest/revisao | payload não autenticado; qualquer cliente com a URL pode enviar diff arbitrário |
| Supabase → backend | service_role key no env do Railway — não exposta ao cliente |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Spoofing | POST /ingest/revisao — project_id no payload | medium | mitigate | verificar que project_id existe na tabela projects antes de qualquer operação; 404 se não existe |
| T-09-02 | Tampering | diff_agregado — prompt injection via diff malicioso | medium | accept | Gemini processa texto, não executa código; achados são apenas lidos, nunca executados; limite 100k chars aplicado no agente |
| T-09-03 | Information Disclosure | relatorio_tecnico com arquivo:linha exposto via bloco_b | low | accept | dados são internos ao DocuData; sem autenticação por escopo do MVP — decisão consciente no design doc |
| T-09-04 | Denial of Service | diff de 100k chars + max_tokens=4096 pode exceder quota Gemini | low | mitigate | gemini_api_key é por projeto; custo recai no projeto; sem rate limiting adicional nesta fase |
| T-09-05 | Elevation of Privilege | agente cliente não tem GEMINI_API_KEY — Gemini fica no backend | low | mitigate | design correto: api_key permanece no Railway; agente usa apenas DOCUDATA_API_URL e DOCUDATA_PROJECT_ID |
</threat_model>
