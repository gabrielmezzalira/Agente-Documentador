<objective>
Wire the new validation node into both ingestion routers. Routers now pass `tipo_esperado`, `force`, `projeto_nome`, `cliente`, and `projeto_descricao` to the graph state. When the graph returns with `valido_tipo=False`, routers raise HTTP 422 with a structured JSON detail (not a 502). The `force` field is accepted as a Form field (multipart) in `/ingest` and in the attachment paths of sprint-docs endpoints.

Purpose: The graph-level validation only fires when the router invokes the graph with the correct context — this plan closes the loop so the graph's output is surfaced correctly to API consumers.

Output: Updated `ingest.py` and `sprint_docs.py` with new form fields and structured 422 error propagation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP form data → router | User-supplied force=True bypasses validation |
| Router → graph state | tipo_esperado is router-controlled, not user-controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-05 | Tampering | force=True form field on /ingest | low | accept | force is an intentional override by the project manager; override is logged in extracted_content as _meta_force_override per Plan 01 |
| T-05-06 | Information Disclosure | 422 detail dict exposes tipo_detectado | low | accept | tipo_detectado is a document category label (e.g. "review") — contains no PII or system internals |
| T-05-07 | Elevation of Privilege | tipo_esperado could theoretically be user-injected | low | mitigate | tipo_esperado is hardcoded per endpoint in router code — it is never taken from user input |
</threat_model>
